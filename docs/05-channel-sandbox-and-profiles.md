# 05 - 社群物理沙箱与成员画像系统

> **版本**：v5.1 (Production Baseline)  
> **模块**：FEAGLE WxBot 社群治理与画像篇  
> **基准代码**：`apps/gateway/src/control.ts` · `index.ts` · `llm.ts`  

---

## 1. 物理级社群沙箱设计原理

传统微信机器人在面对多群并发交互时，通常将所有群聊的消息堆叠在同一内存空间中，导致三个致命缺陷：
1. **跨群数据越权**：群 A 的机密技术讨论被大模型当成上下文在群 B 脱口而出；
2. **规则配置僵化**：无法做到技术群严谨务实、运营群幽默活跃，全平台只能采用同一套单一 Prompt；
3. **安全风险扩散**：一旦一个群聊遭到群友恶意注入测试，整套系统的人设全局崩塌。

FEAGLE 网关提出了**物理级社群沙箱（Per-Chat Physical Sandbox）**标准：网关在数据底座上为每一个进站的微信群分配专属的独立物理文件夹。

---

## 2. 沙箱物理目录结构与文件规格

每个群聊在 `data/channels/<chatId>/` 路径下独立落盘，结构如下：

```text
data/channels/19827364501@chatroom/
├── meta.json       # 群元数据与自定义别名
├── persona.md      # 该群专属人设 Prompt (最高优先级，覆盖全局)
├── rules.md        # 该群专属安全铁律与红线守则
├── tools.json      # 该群授权的工具白名单清单
├── members.json    # 群成员画像与标签沉淀数据库
└── memos.json      # 该群专用的本地备忘录降级存储
```

### 2.1 文件功能与契约格式

#### 1. 群元数据 (`meta.json`)
```json
{
  "name": "FEAGLE 核心架构攻坚群",
  "chatId": "19827364501@chatroom",
  "createdAt": 1731300000000,
  "updatedAt": 1731386400000
}
```
* **作用**：存储管理员为该群设定的自定义易读中文别名，支持通过控制台或 `/name` 指令热更新。

#### 2. 群专属人设 (`persona.md`)
* **作用**：纯 Markdown 文件。优先级高于系统默认人设，专门定义该群专属的说话语调、专业领域背景以及回复偏好。
* **例如**：在运维群设定为“严谨、精简、给出排查命令”，在萌宠群设定为“温暖、活泼、多使用生图工具”。

#### 3. 群专属安全铁律 (`rules.md`)
* **作用**：纯 Markdown 文件。网关在最终生成 System Prompt 时，将此文件内容强制拼装在最末尾（`[不可逾越的安全红线]`），对大模型形成强约束。
* **例如**：“严禁透露公司服务器内网 IP，严禁在群内讨论政治与涉敏话题，被问及时代替以礼貌拒答”。

#### 4. 工具授权白名单 (`tools.json`)
```json
[
  "web_search",
  "generate_image",
  "read_wechat_article",
  "group_remind",
  "palace_memo"
]
```
* **作用**：JSON 数组。精确约束该群在大模型 Function Calling 时允许调用的工具集合。即便某工具在系统全局已注册，若未出现在该群的 `tools.json` 中，大模型也无法调用，物理拦截越权。支持 `["*"]` 开放全量。

## 3. 微信真实群名实时解析与双层呈现

### 3.1 协议 ID 弊端与解析算法
在微信底层网络协议中，群聊 ID 均为无规则的十六进制字符串（如 `19827364501@chatroom` 或 `24871928374@chatroom`）。若在 Web 管理后台直接展示原始 ID，管理员完全无法分清哪个卡片对应哪个微信群。

FEAGLE 网关与 Bridge 协同实现了**真实群名三级解析决议算法 (`resolveRealGroupName`)**：

```text
               ┌────────────────────────┐
               │ 获取群聊展示名称       │
               └───────────┬────────────┘
                           ▼
          ┌──────────────────────────────────┐
          │ 检查沙箱 meta.json 是否有别名？   │
          └───────┬──────────────────┬───────┘
             YES  │                  │ NO
                  ▼                  ▼
          ┌───────────────┐  ┌──────────────────────────────────┐
          │ 返回用户自定义 │  │ 检索 mapping.sqlite 通讯录表？   │
          │ 别名 (Name)   │  └───────┬──────────────────┬───────┘
          └───────────────┘     YES  │                  │ NO
                                     ▼                  ▼
                             ┌───────────────┐  ┌───────────────┐
                             │ 返回真实微信群名 │  │ 保底回退展示  │
                             │ (如 "攻坚群") │  │ 原始 ID 字符串│
                             └───────────────┘  └───────────────┘
```

1. **第一优先级**：读取沙箱 `meta.json` 中由管理员手动设定的易读别名（`name`）；
2. **第二优先级**：跨库查询 Bridge 的 `data/wechat/mapping.sqlite` 中由 Android Hook 自动同步的通讯录 `contacts` 表真实中文群名；
3. **保底回退**：若为全新未命名群聊，回退展示原始 `@chatroom` 字符串。

### 3.2 控制台双层拟态 UI 呈现
在 Web 控制台的沙箱网格与配置抽屉顶部：
* **首行高亮**：以大号加粗字体展示真实中文群名；
* **次行辅助**：以等宽字体展示底层群 ID，右侧附带一键复制小按钮，兼顾人性化日常识别与工程底层排错需求。

## 4. 群成员画像与标签自动化沉淀 (Member Profiling)

### 4.1 成员画像数据结构 (`MemberProfile`)
在群聊沙箱中，系统维护 `members.json` 文件，以群成员的微信 wxid 为键建立细粒度画像：

```typescript
export interface MemberProfile {
  wxid: string;             // 成员微信底层全局唯一 ID
  nickname?: string;        // 最近一次观察到的微信昵称
  role?: string;            // 角色定位 (如: "系统核心架构师", "前端负责人", "实习生")
  tags?: string[];          // 能力与关注标签云 (如: ["Vue3", "TypeScript", "性能优化"])
  notes?: string;           // 协同批注 (如: "对代码类型要求极高，不要输出 any")
  interactionCount: number; // 累计互动提问次数
  lastActive: number;       // 最近活跃时间戳 (毫秒)
}
```

### 4.2 自动化追踪与沉淀机制
* **轻量自动化更新**：当群成员在微信群内发言或提问时，网关在进站拦截时自动递增该成员的 `interactionCount`，更新其最新昵称与 `lastActive` 活跃时间；
* **控制台可视化编辑**：管理员可在 Web 后台的“成员画像”抽屉中，直观检视该群的所有发言成员列表，并点击任意成员弹窗赋予其角色、能力标签与工作关注批注。

### 4.3 Prompt 动态注入与个性化应答机制
当某位已有画像标签的群友在群内 `@Nox` 提问时，网关在组装大模型上下文时，自动在 System Prompt 顶部动态注入该成员的画像卡片：

```text
[当前提问成员身份画像]
提问者昵称: 逍遥子 (wxid_x9823kd)
群内角色定位: 系统核心架构师
技术/业务标签: Vue 3.5, 严格类型系统, 分布式网关
协同注意事项: 对代码严谨度要求极高，给出方案时优先考虑类型安全与边界容错
```

**业务收益**：
* 面对同一技术问题，若提问者是“架构师”，大模型自动输出高深度的架构演进与并发边界考量；
* 若提问者画像为“初级研发/业务新人”，模型自动输出通俗易懂的拆解说明与基础操作步骤，大幅提升回答的命中率与群友满意度。

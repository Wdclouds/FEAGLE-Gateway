# 07 - 移动硬件拦截与协议桥接

> **版本**：v5.1 (Production Baseline)  
> **模块**：FEAGLE WxBot 移动硬件与底层拦截篇  
> **基准代码**：`apps/android-agent` · `apps/bridge/src/android-client.js` · `dashboard.js`  

---

## 1. 物理真机基线环境标准

为了彻底根除封号风控，FEAGLE WxBot 规定必须在真实合法的移动硬件上运行，拒绝任何无界面的虚拟化模拟器或破解协议。

### 1.1 硬件与固件基线参数
* **标准测试与生产设备**：Samsung Galaxy Tab A8 (型号：`SM-X200`)；
* **处理器架构**：Unisoc Tiger T618 (Octa-core 2.0 GHz, ARMv8 64-bit)；
* **运行内存与存储**：4GB RAM + 64GB 内部存储；
* **操作系统版本**：Android 14 (One UI Core 6.0 官方稳定版)；
* **底层 Root 框架**：Magisk 30.7 + Zygisk 运行模式；
* **Hook 注入框架**：LSPosed / Vector 框架模块；
* **宿主微信版本**：微信官方 64 位 APK 架构 `8.0.78` (`arm64-v8a`)。

## 2. Android Hook 拦截与事件监听机制

### 2.1 物理事件截获原理
安装在平板系统中的 `feaglewxbot-agent` 通过 LSPosed 模块加载进官方微信进程的内存空间中：
1. **数据库写入拦截**：Hook 挂载于微信底层 SQLite 消息存储的关键函数（如 `message.insert`）；
2. **元数据提取**：
   - 提取全局唯一消息 ID（`msgSvrId`）；
   - 提取真实会话标识 `talker`（如 `19827364501@chatroom` 或私聊 `wxid_xxx`）；
   - 提取群聊内部真实发信人 `senderWxid`；
   - 提取原始消息文本内容与消息类型码（文本、图片、引用回复等）。
3. **系统噪声过滤**：
   - 拦截层自动丢弃公众号（以 `gh_` 开头的通知推送）、微信团队号、文件传输助手、群系统折叠提示（如“xx 邀请 xx 加入了群聊”）等非人类交互噪声，仅将真正的群聊与私聊消息打包向服务器投递。

### 2.2 媒体格式转码兼容 (wxgf HEVC 转码)
微信在移动端为了节省流量，对用户发送的部分动图或视频流采用私有的 `wxgf`（基于 HEVC/H.265 编码）格式存储。大模型等多模态上游接口无法直接识别此类私有格式。
* Bridge 在接收到图片事件时，通过服务器端内嵌的 `ffmpeg` 流处理管道，将私有媒体即时转码为标准的 JPEG 图像数据；
* 同时提取图片的缩略图与高清原图二进制流，生成 Base64 编码供网关 L1 意图路由层直接作为多模态视觉上下文进行理解。

## 3. 扫码免密配对与双向 WebSocket 通信协议

### 3.1 动态凭证免密配对 (`PairingStore`)
平板与服务器之间采用 WebSocket 长连接通信（监听端口 `0.0.0.0:6191/android`）。为防止内网未授权设备非法接入：
1. 管理员在 Web 控制台点击打开“设备连接向导”；
2. Bridge 在内存中生成一个有效周期为 **5 分钟的高强度随机 Ticket 与 配对 Token**，并编码为连接二维码；
3. 平板端打开 Android Agent 点击“扫码配对”，扫描控制台上的二维码；
4. Agent 读取服务器 IP、端口与 Token，发起 WebSocket 握手并持久化保存凭据；
5. 后续无论平板发生网络波动重连或重启，均通过持久化的 Token 自动发起免密重连与保活握手。

### 3.2 链路保活与心跳自愈机制
* **75 秒心跳保活**：平板端每隔 25 秒向 Bridge 发送一次 `PING` 帧，Bridge 应答 `PONG`；
* **断线自动重连**：当超过 75 秒未收到平板心跳时，Bridge 自动标记设备进入离线状态，并在 Web 控制台上亮起琥珀色告警呼吸灯；
* 平板端的 Android 守护服务通过前台通知服务常驻保活，一旦感知网络恢复，自动按指数退避算法（1s, 2s, 4s, 8s... 最多 30s）重新发起建连，实现全天候 24 小时无人值守。

## 4. 出站高清大图流式直拉防阻塞设计 (`OutboundImageStore`)

### 4.1 传统 Base64 直推的信道阻塞痛点
在大模型生成一张 1.3MB 甚至更高的 PNG 高清图片时，若直接将图片的完整 Base64 报文通过 WebSocket 发送给平板，会引发**队头阻塞（Head-of-Line Blocking）**：
* 几兆的巨型二进制流长时间占用唯一的长连接通道，导致其间发生的正常文字收发被严重挂起堵塞，甚至因超时引发连接断开。

### 4.2 动态 Ticket 分块直拉架构
FEAGLE 体系设计了**大文件 HTTP 临时分发直拉机制**：

```text
[Gateway 生成图片] ──> 本地文件: gen-1234.png
                             │
                             ▼
[Bridge 接收发图指令: { img: filePath }]
                             │
                             ▼
┌────────────────────────────────────────────────────────┐
│ OutboundImageStore 临时凭据分发中心                    │
│                                                        │
│ • 生成 60 秒有效期的随机临时 Ticket: tk_98234          │
│ • 向 WebSocket 发送轻量通知指令:                       │
│   { action: "PULL_IMAGE", url: "/api/img/tk_98234" }   │
└──────────────────────────┬─────────────────────────────┘
                           │ 仅传输十几个字节的通知
                           ▼
┌────────────────────────────────────────────────────────┐
│ 物理平板 (SM-X200 Android Agent)                       │
│                                                        │
│ • 主 WebSocket 信道完全不被阻塞，文本秒级交互          │
│ • 启动后台独立 HTTP 线程拉取二进制图片流               │
│ • 下载完毕后，调用微信底层发送原生图片                 │
│ • 销毁 Ticket，清理平板与服务器临时内存                │
└────────────────────────────────────────────────────────┘
```

这一精巧的流式设计彻底解耦了长连接指令通道与媒体传输通道，确保系统无论并发生成多少高清大图，微信日常文字互动始终维持在毫秒级极速响应。
